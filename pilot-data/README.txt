UAE and India pilot validation inputs

UAE/ and India/ contain redacted-inputs, independent-expected-results and review-records folders, plus a manifest template. These folders currently contain no real client files or professional approvals. Their contents are ignored by Git; the empty structure and manifest templates are saved in the repository.

synthetic-examples/ contains the existing authored engine scenarios with their literal input sources and expected behavior. Every example is labelled SYNTHETIC_ENGINE_FIXTURE and is not client data or a country legal qualification. The catalog preserves the source fixture hash and country/workflow. Additional native-format examples remain under docs/country-workflows/sample-inputs/.

For a real pilot, save authorized redacted originals in the relevant country input folder. Save independently prepared expected results separately, then record the actual input hashes, period, preparer and independent reviewer in a working copy of the manifest under review-records. Expected results must be checked independently of the software output. Record actual comparisons, unresolved cases and review conclusions without replacing original evidence.

Regenerate unchanged synthetic examples with backend/.venv/Scripts/python.exe scripts/export_country_pilot_examples.py. Existing differing case files are preserved rather than overwritten.

The current executable catalogue contains 164 synthetic engine fixtures (106 UAE, 58 India), saved under synthetic-examples/versions/icfr-duty-coverage-2026-10-31/. The historical root catalogue retains its 154 cases (101 UAE, 53 India). Some historical cases lack later explicit currency controls, so the new version preserves those originals instead of replacing them. Unchanged example files keep their original bytes and historical source-fixture hash when the fixture source gains cases. The catalogue records each file's original hash and the current generator source hash separately. A change to the case, its expected result or other metadata still stops regeneration for manual preservation; it is never silently overwritten. These hashes identify fixture versions, not professional validation.

Local comparison: scripts/validate_country_pilot.py checks declared retained hashes, country/workflow scope, separate preparer/reviewer records and exact expected-versus-actual JSON. See README.md for the command, manifest states, review template and file limits. Exit 0 means declared evidence matches, not professional or legal qualification. No real pilot is supplied or completed by creating these folders.

ICFR duty examples RW-155 through RW-164 retain explicit fictional authority and scope-document UUID/hash placeholders. These exercise CSV parsing and the deterministic engine only; their placeholders are not uploaded originals or verified evidence bindings. Production source import requires actual clean retained files and their exact current hashes. Use the separately saved ICFR upload bundles under docs/country-workflows/sample-inputs/SYNTHETIC-icfr-duty-coverage/ for the upload instructions.

Exports now automatically retain exact generator input bytes under fixture-sources/<SHA256>.txt, including original line endings. The catalogue lists every referenced source hash as RETAINED or HISTORICAL_BYTES_NOT_RETAINED. Re-export preserves prior case files and source snapshots, refuses altered snapshot bytes, and does not manufacture missing historical originals.

In the application, expand synthetic reference scenarios in Country workflows. The list starts with this engagement country and selected workflow. Country/workflow filters and search let reviewers inspect the full catalogue, each labelled country and expected synthetic result. Browsing examples does not change the selected engagement, workflow inputs or country rules. An empty search result is not a nil client population.

The capabilities and engagement country-workflow APIs expose reference_scenario_evidence with the synthetic dataset kind, count basis and country counts. The historical real_world_scenario_count capability field is retained as a synthetic fixture count, with its meaning stated in that metadata. Execution evidence comes from source-specific receipts; the catalogue itself does not establish client validation.
