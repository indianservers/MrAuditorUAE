# Security baseline and deployment limits

Passwords use Argon2id. Bootstrap requires an explicitly configured secret and is serialized with a PostgreSQL advisory lock; any existing user blocks a second initialization. Bootstrap creates a Firm Administrator, not a platform superuser. Disable the setup secret afterward. Production settings reject enabled bootstrap and signing secrets shorter than 48 characters.

OAuth2 form login returns short-lived signed access JWTs with required subject, expiry, issue time, issuer, audience and token type. Opaque refresh secrets are random and hashed at rest. Rotation row-locks the session and records the successor in the same family. Replay revokes every family member even when returning an error. Logout revokes the family. Existing access JWTs expire naturally; user/membership disabling is checked immediately on later calls. The system does not yet provide MFA, SSO/OIDC, password reset, account invitation or a user/role administration API. The identity module and membership mappings are the integration boundary for those additions.

Nine role definitions map to permission codes. Platform Administrator receives only platform.manage and has no automatic client access. Firm Administrator has tenant resource permissions. Client Viewer has tenant-wide metadata read access, not client-specific filtering. Do not invite external client users until engagement/client grants exist. Role assignment is deployment/database administration only in this phase; no arbitrary public signup or self-elevation exists.

Services scope data by a verified tenant Context and repositories include tenant predicates. Composite FKs prevent cross-tenant relationships. Forced RLS checks transaction-local tenant context on all owned business/job/AI/audit tables. PostgreSQL initialization creates an app role with NOSUPERUSER, NOCREATEDB, NOCREATEROLE and NOBYPASSRLS. Readiness rejects superuser/bypass roles. The local Compose app role owns its schema to support migrations; production must split an offline migration owner from a non-owner runtime role and grant only required DML. FORCE RLS protects against accidental owner bypass but a schema owner could deliberately alter policies; RLS is defense in depth, not protection against compromised database-owner credentials.

Authentication POST routes use Redis-backed atomic per-IP 20-per-minute limits, fail closed if Redis is down, and do not trust arbitrary forwarded IP headers. Configure the reverse proxy/client-address boundary before multi-node deployment, and add account-based protections. Inputs reject unknown fields where relevant, UUIDs are validated, sort columns are allowlisted, SQL values are bound parameters and resources support optimistic locking. Bodies are counted while streaming, including chunked transfers. Add proxy-level slow-client/body timeouts and request limits in production.

CORS is an explicit allowlist; TrustedHost validates hosts. Security headers include nosniff, DENY framing, no-referrer and no-store, plus HSTS in production behind HTTPS. JSON logs use an allowlist of fields and exclude headers/bodies/token/password/provider error content. Authentication denials and refresh replay produce safe security events. Successful resource and bootstrap operations append database audit rows; triggers reject audit UPDATE/DELETE through normal DML. Privileged DDL can still alter/truncate tables: restrict DB administrator access and export audit logs to an external immutable sink for production. Failed-login events live in structured logs because unauthenticated identities have no verified tenant context.

## Backups and operations

Use encrypted daily PostgreSQL logical backups plus continuous WAL archiving for point-in-time recovery. Keep encryption keys and backups outside the workload account, restrict restore permissions, define retention and UAE data-residency requirements, and conduct documented restore drills. Named Docker volumes provide persistence, not backups. Take a backup and test migration compatibility before upgrades. Redis is a delivery mechanism; PostgreSQL job rows are the durable status/idempotency source. Republish pending jobs with the original idempotency key after broker failure.

Before production: enforce TLS at a trusted ingress, isolate database/Redis networks, authenticate Redis, separate schema-owner/runtime roles, manage secret/key rotation, pin and scan container digests, remove development tools from a production image, add MFA/invitations/client grants, monitor errors/queue lag and audit events, verify backups/restores, conduct independent security review and load tests, define incident response and retention policies. Compose is local development infrastructure, not a production deployment certification. Local test runtimes used only loopback and a disposable database; temporary trust-authenticated PostgreSQL is not an installation recommendation.

## Phase 2 controls

New financial operations use distinct accounting/import/mapping/analytics/sampling/connector/financial-AI permissions. Firm Administrator initially receives them; client/platform roles do not. Scoped composite FKs and forced RLS cover every new table. Native source files and raw API pages remain private/versioned; production S3 requires KMS and versioning. OAuth credentials are encrypted at rest with an independently injected Fernet key. OAuth state expires and is consumed once. The Windows connector keeps refresh credentials in the OS vault and requires verified HTTPS to AuditOS. XML entity expansion, workbook macros/formulas/external links and archive bombs are rejected. Structured suggestions require explicit review and cannot mutate immutable ledger rows. Large counted uploads bypass the small JSON-body ceiling but retain a finite source limit. Add production upload quotas/retention, secret re-encryption rotation, private-object backup drills and live connector/IAM testing before customer deployment.
# Phase 12 security changes and limits

Issued access tokens bind to revocable refresh sessions; production rejects unbound development fixture JWTs. Encrypted RFC6238 authenticator MFA rejects replayed counters. Platform operators always need a separate grant and verified MFA; production protected APIs require verified MFA. Demo flags/database names and synthetic tenant markers block production startup/readiness. No support impersonation bypass was added.

Current evidence and open risks: `phase-12/security-assessment.md`, `asvs-assessment.json`, dependency/SAST/secret reports and defect register. ASVS5.0.0 is the primary assessment reference; no complete ASVS, penetration-test, malware scanner or hosted container clearance is claimed. Production remains NO-GO. Retention/DSR, legal applicability, live scanner, hosted monitoring/recovery and deployment rollback require independent acceptance.
