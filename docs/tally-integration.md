# TallyPrime local connector

The adapter follows the supported [native XML envelope/collection structure](https://help.tallysolutions.com/understanding-tally-xml-tags/) and [Tally integration methods](https://help.tallysolutions.com/integration-methods-and-technologies/). It builds read-only Export requests with company/period variables and a date-filtered voucher collection. It supports Company, Group, Ledger and Voucher collections; different Tally/TDL configurations may require a reviewed export customization.

`agents/tally_agent.py` is a manual Windows agent foundation. Install the backend uv environment, configure TallyPrime's HTTP/XML server on localhost:9000, keep the Tally port private, and store the non-secret agent configuration in a private NTFS directory. The configuration contains server_url (HTTPS required), tenant_id, client_id, entity_id, period_id, company, start_date, end_date and currency; tally_url is optional but restricted to loopback.

From backend, run `uv run python ../agents/tally_agent.py PATH_TO_CONFIG --set-refresh-token` to save an authorized AuditOS refresh credential in the OS credential vault. Then run the same command without that flag to refresh the access token, extract and preserve a .tally.json package, upload resumable chunks, and queue validation. Keep the package private. `--resume PACKAGE` reuses extraction output and previously received chunks after interruption. An agent lock prevents concurrent refresh-token rotation for the same configuration. Errors do not print credentials.

The original company/groups/ledgers/vouchers XML responses are preserved as base64 bytes in the package. Server parsing uses defusedxml, validates voucher IDs/dates, native debit-negative/credit-positive signs, amounts, ledger references and balanced voucher totals, and retains source group/cost-center information where present. Missing masters produce warnings; missing/duplicate voucher IDs and unsupported currency-format amounts fail. The common accounting normalizer repeats financial-period and precision checks. Package upload does not activate a ledger automatically; validation/reviewer-controlled commit remain separate.

Company verification is explicit: the parser records whether company identity actually appeared in the export. Configuring a company is not proof that the returned company matched if the export omits identifying fields. Request source control totals/counts and compare a Tally GL/TB report before asserting completeness. Opening balances from masters are retained as source data; import the independently controlled opening/TB report for ledger roll-forward rather than inventing opening journals.

Realistic XML parser tests and resumable server-upload tests pass. Optional LIVE_TALLY_SMOKE requires an explicitly authorized local Tally installation and company. No actual Tally instance or complete Windows credential-vault/extraction/HTTPS session was available; no end-to-end Tally certification is claimed. Automatic Windows service installation and a long-running scheduler are not included.

Version 3 adds `--kind all` (the default), or `--kind gl`, `--kind coa`, and `--kind tb`. The same preserved native package is submitted as separate populations with separate `.gl.resume.json`, `.coa.resume.json`, and `.tb.resume.json` files. Resume state binds the package hash to tenant/client/entity/period/company/currency and kind. New packages record company and period. Cancelled, optional and deleted vouchers are excluded from posted movements and counted; their XML remains preserved.

Chart import uses native ledger masters. TB import requires native numeric opening AND closing balances for every ledger and reconciles their roll-forward against posted voucher movements. It blocks when a master is missing, a balance is absent, or the native balance date context does not match the period. It never replaces absent closing balances with a calculated value. Native master opening values can depend on books/financial-year context; verify a mid-year period explicitly during live qualification. If a Tally/TDL configuration does not provide the necessary balances, use a period-specific TB CSV/XLSX export through the report-set importer. GL voucher movement extraction does not fabricate opening journals.

The Integration Center also accepts a Tally XML/JSON package directly after selecting TallyPrime, the exact company name, and GL/COA/TB population type. Source-company mismatches and conflicting company declarations fail. Independent source reports and reviewer activation remain required.


## Windowed extraction, identity and service source

The current agent writes `.tally.ndjson` packages. `--window-days 31` is the default; narrow it when a single XML response exceeds 64 MiB. Masters and company identity are captured once, then contiguous voucher windows are written independently. NDJSON import retains original XML and rejects missing terminal coverage. The configured upload/storage limits still bound the complete package.

On initial extraction the agent prints a company fingerprint. Verify the company, enroll that fingerprint in the connection's **Sync health and recovery** panel, and copy it to `company_fingerprint` in the agent configuration. Later GUID/statutory/books-date mismatches stop extraction. Upload options can carry `tally_company_fingerprint` for server-side verification. The same panel compares a stored GL batch's voucher revisions, including cancellations, without activating it.

`agents/windows_service.py` is a service source, not an installed or signed executable. Install backend dependencies plus `agents/requirements-windows.txt` into the compatible Windows Python environment. The service reads `%PROGRAMDATA%/AuditOS/Tally/config.json`, including an absolute `python_executable`, and writes a separate protected `runs` directory for each extraction. Run it under the Windows account enrolled in the credential vault. Restrict configuration/run-folder access to administrators and that account. SDK/service packaging and Windows qualification remain release work.

`agents/install-tally-service.ps1` requires a built executable, approved SHA-256 and pinned publisher thumbprint. It rejects unsigned/untrusted artifacts before service changes. `-Update` switches to a verified new binary and restores the earlier binary path if startup fails; it does not download arbitrary updates. Supply the release signing certificate through the release process, never through chat. No signing certificate or signed artifact is included in this change.
