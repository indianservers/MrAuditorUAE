# Phase 5 — final foundations and verification

This phase strengthens existing compliance, AI and connector services. It does not certify production readiness, invent legal defaults, enable financial execution or add use cases. Existing unrelated workspace changes are preserved.

## Working changes

**E19:** Obligations can retain an unresolved deadline instead of an invented date. Optional versioned calendar rules record validity, trigger/date basis, month/day offsets, IANA timezone, explicit weekend/holiday convention and supporting approved evidence. Calculated obligations require evidenced entity facts; period-end triggers must match the engagement. Extensions retain separate evidence and dates. Changes remain in immutable audit revisions and source changes require reassessment through existing lineage checks.

Filing stage is separate from workpaper approval: not started → preparing → under review → approved for submission → submitted → acknowledged. The versioned filing-stage endpoint rejects jumps, missing readiness evidence, unresolved blockers, stale dependencies and version conflicts. A designated independent reviewer attests approval for submission; retained submission and acknowledgment documents are separate. An export does not advance a filing stage. Repeating a stage does not restore approval or alter evidence. Locked records and closed periods cannot be changed through this route. Recording a submission receipt is a human attestation; the system does not contact an authority or authenticate an authority's acceptance.

The compliance calendar exposes unresolved dates, filing status, review status and source freshness separately. Opt-in reminder offsets and escalation rules create deduplicated in-app history using the existing notification store; no external message is sent. Automatic discovery of every entity's legal obligations, background automatic draft recalculation and external delivery remain incomplete. New calculated deadlines are produced when the user saves a reviewed revision; approved historical records remain unchanged.

**E21:** A scoped runtime-status endpoint separates the language gateway from local ML. It exposes not configured, diagnostic mode, configured/unverified, disclosure blocked, recently reachable and failing states. Reachability comes from the tenant's recent execution record with a five-minute window; it is not a fresh probe or proof that a changed provider configuration works. It returns no key or gateway URL. The command center displays this state. Existing narrow allowlisted tools now publish their strict schema and consequence class. Approved evidence retrieval also rechecks source freshness before use. Retrieved text cannot replace typed input scope, the allowlisted plan or the independent approval service.

Existing deterministic engine adapters, local ML, immutable tool receipts, grounded citations, bounded context/tokens, step timeouts, cancellation and approved draft execution remain authoritative. Language output has no action channel and cannot approve itself. The AI demonstration uses the existing phase11 test's actual authorized retrieval and draft-action workflow with a clearly labeled diagnostic narrative, not a live language-model verification claim.

The full campaign also exposed a shared operational defect: readiness still expected migration `0018`, rejecting the correctly migrated database and production worker admission. The release contract now expects `0020`, with a test comparing it to the actual Alembic head. Two old synthetic fixtures were corrected: analytics now declares its operating calendar, and the trading scenario establishes its chart before approving IFRS/tax inputs. The stale-package guard remains enforced.

**E22:** Connector health now exposes last attempt/success, bounded-history lag, counts, checkpoint counters, error category, completeness and remediation. A failed or incomplete latest attempt cannot inherit the completeness of an older success. Summary payloads exclude arbitrary provider fields and credentials. Existing edition-specific transport, encryption, OAuth/token refresh, origin-pinned pagination, durable checkpoints, source revisions, webhook verification and independent controls remain in use. The connector workspace displays the health summary. No live provider has been qualified by these tests, and file imports remain labeled adapters.

## Verification and scope

Use [verification.json](verification.json) for retained final test counts and hashes. Reports distinguish focused tests, the broad backend regression, frontend checks and local TensorFlow.js execution. Controlled failure tests use labeled transport/scanner/broker doubles; these do not establish live integrations. No external AI credentials, payments, postings, messages or authority submissions are used in the demonstrations.

The initial full backend campaign passed 1,250 tests with 8 skipped and exposed 4 failures. After the fixes, all 41 affected integration tests and 769 unit/provider tests passed (4 unit skips). The four separately gated connector PostgreSQL/Redis tests then passed in their dedicated ephemeral database. The combined index records **1,273 distinct latest passing backend results, zero unresolved failures and 4 skips**, using the initial campaign plus post-fix/isolated reruns; it is not a second uninterrupted full run. The remaining skips are authorized-live-provider smoke tests. All 69 frontend tests and 7 TensorFlow.js tests passed; frontend typechecking and scoped lint passed. The initial failures remain in `backend-initial-results.xml` and `backend-results.xml` for auditability.

- `compliance-runtime-connector.json`: unresolved deadline, filing stage/version guards, independent review, gateway independence and incomplete connector status.
- `filing-lifecycle.json`: readiness evidence, reviewer attestation, separate submitted/acknowledged records, reminder duplicate suppression and stale receipt detection.
- `restore-results.json`: actual synthetic PostgreSQL dump restored into a new isolated database, with all public table counts and copied private-object hashes compared. This is a single-host recovery test, not an RPO/RTO certification or credential-rotation test.
- `worker-recovery.json`: a controlled persisted expired-claim condition becomes a failed job requiring manual retry; a pending outbox record is dispatched. This does not claim that a production worker was killed and recovered during a real financial action.
- Prior connected trading/tax, group/accounting and audit/operations demonstrations remain under Phases 2–4. Their limitations remain open. The regression reruns their available test paths; it does not create a newly approved end-to-end client reporting pack or qualify a complete free-zone/group tax engagement.

## What operates with each dependency

- **Without external AI credentials:** controlled ingestion, deterministic financial/tax calculations within supported cases, reviewed evidence, rules analytics, explicit statistical/rules baselines, compliance records and in-app notifications. Client rules, mappings, facts and source completeness still require approval.
- **With available approved local models:** TensorFlow.js inference after scoped artifact/schema/hash and deployment checks. Synthetic training/reload tests do not establish client predictive quality. No client-ready trained model is assumed available.
- **With a configured language gateway:** optional grounded narrative drafts subject to disclosure approval, approved model selection, budgets and citations. Current local configuration presence check reports no selected model/key/disclosure approval. No live gateway call was made here.
- **With authorized external connectors:** supported edition-specific extraction and recovery paths can be qualified against independent counts and financial controls. Current tests use controlled transports; no authorized live account is claimed. Use controlled file imports until qualification is complete.
