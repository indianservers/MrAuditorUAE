# Reuse reviewed supporting bank tables

Country workflow sources can now reuse a current, independently reviewed bank table from the existing Supporting tables workspace. This avoids downloading a normalized table and uploading it again as another CSV. It reuses the original retained evidence, scoped event permissions, immutable review versions and dependency graph.

In **Prepare sources**, select **Reviewed supporting bank table** as the origin. Choose a reviewed current bank table, declare the bank account identifier and account-scope assessment, then enter independent row and currency totals. The source contains every reviewed table row; it does not filter, truncate, assign a currency, invent dates or infer account ownership. Where the normalized table declares an account code, every row must agree to the selected identifier. Otherwise the scope assessment is the explicit declaration, requiring independent review against original evidence.

The bridge is bounded to one through 5,000 rows and the existing 10 MiB original-file verification limit. It rejects unreviewed or stale tables, other table kinds, mismatched original evidence versions, inconsistent population receipts and conflicting accounts. Additional CSV mappings and debit/credit transformations cannot be layered onto this bridge. The table's existing date/decimal normalization is reused as reviewed input; it is not rerun under new settings.

The prepared source retains original source-row numbers, supporting-table version ID, scope assessment, original filename and evidence hash. Original download remains byte-for-byte the uploaded evidence. The source result provides an action to open the reviewed supporting table. Exports retain the bridge basis and scope. The supporting table's original creator and reviewing actor propagate as contributors, so a prior contributor cannot independently approve the bridged source.

Review the prepared workflow source independently before final result approval, as with other sources. A bank reconciliation consumes it through the normal statement role with independent cashbook and opening/closing controls. Replacing original evidence or changing a supporting-table version makes dependent source and reconciliation results stale. Reuse never establishes two independent roles from the same evidence: the existing identity and hash safeguards continue to apply.

The supporting bank/open-item reader accepts CSV and the bounded [value-only XLSX profile](supporting-spreadsheets.md). This page describes the bank bridge; the additional [open-item profile](supporting-open-items-bridge.md) requires explicit side, document classifications, dates and sign assessment. Neither profile qualifies PDF/image extraction, arbitrary OCR tables or account ownership. Those remain separate roadmap work.

Verification: `supporting-bank-unit-results.xml` contains 261 targeted regression tests, including twelve bridge cases. `supporting-bank-integration-results.xml` contains three database/API tests covering the bridge and CSV import paths. The bridge test exercises explicit date/decimal normalization, unreviewed rejection, independent review, original bytes, account/count controls, cashbook reconciliation, contributor separation and staleness through original-evidence replacement. Seventeen workflow UI tests, frontend production build, frontend type checking, source-schema type checking and scoped lint pass. Database verification uses explicit scanner/broker doubles and does not certify production services or a client pilot.
