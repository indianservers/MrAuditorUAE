# Source snapshots and lineage

Source files are never publicly served or overwritten. The development ObjectStore writes exclusive UUID-named private objects. Production requires an S3 bucket with versioning enabled and KMS encryption; bucket, region and KMS key come from server configuration. IAM must deny public access, restrict tenant object prefixes as operationally appropriate and protect source versions from deletion. The adapter verifies versioning, requires all four S3 public-access-block controls plus an explicit KMS key, and retains the returned VersionId. An S3 integration test is not a substitute for a live IAM/KMS/retention review.

Import files store original filename, object key/version, SHA-256 and byte count. Import snapshots store immutable file/mapping/connector/options manifests and their SHA-256, scope, creating user and UTC extraction/upload time. Hash verification precedes validation. Each source_records row contains original tabular row values (or a versioned connector row projection linked to the preserved native response), canonical staged values, source identifier, row position and a record hash. Files, snapshots, source rows, transformations and journal facts have database UPDATE/DELETE rejection triggers. Versioning is append-only; lifecycle states live separately on import_batches.

Lineage is: Finding → rule result/run and version → journal line/journal → original source row → import snapshot → exact original file version/hash. The security-invoker record_lineage view and GET /accounting/lineage/{line_id} expose this chain to authorized tenants. Source record versions are represented by immutable rows belonging to distinct import snapshots, exposed through the source_record_versions view rather than duplicating raw JSON.

Zoho sync manifests preserve exact received API page/detail bytes in private hashed objects. Derived chart/manual-journal imports retain source_sync_run_id in their immutable options, which connects normalized CSV rows back to the original API extraction manifest. Partial pages remain recorded with failed/insufficient_evidence status. The Tally agent preserves exact HTTP/XML response bytes inside a base64 JSON package; the package is hashed/versioned before safe XML parsing.

Normalized ledger activation uses an explicit supersedes_id workflow. Historical ledger rows are retained, and the canonical GL view selects active batches only. Mapping changes append profile versions and historical analytics retain the mapping evidence used. Replacing financial facts or accepting an AI observation cannot silently overwrite an original source. Object retention, legal holds, cross-region residency, orphan-object housekeeping and immutable backup enforcement require production operational policies; they are not implied by a Docker named volume.
