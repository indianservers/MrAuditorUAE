# Connector architecture

Connectors extract authorized source material; canonical normalization and financial validation remain separate services. Connections are scoped to a verified tenant/client/entity/period. Connection credentials are encrypted using an independently injected Fernet key, excluded from serializers and logs. The key must live in a production secret manager with a tested re-encryption rotation/backup procedure. A database dump alone must not contain usable connector credentials.

Zoho uses allowlisted regional accounts/API domains and OAuth state/refresh handling. Version 3 paginates all chart accounts and their account transactions, staging system-generated and manual postings as a GL import. Raw pages and manual-journal details remain preserved; invoice/bill/credit-note/contact lists remain supporting evidence. This expands coverage but is not live certification. Reconciliation remains insufficient_evidence until independent accounting reports/counts/totals are supplied.

Tally uses an outbound local Windows Python agent and native HTTP/XML collection exports. Tally ports remain loopback-only. Packages travel to AuditOS over verified HTTPS and resume using numbered hash-verified chunks. XML parsing is hardened against external entities and unsafe documents; company, voucher IDs/dates/signs and ledger presence are validated where supplied.

Connection synchronization and import parsing can run through existing Celery/Redis infrastructure. Work restores tenant context, checks current operation permission and identity/membership/tenant activity, row-locks work, and persists progress/status/result references. Sources and failed imports do not become active ledger populations. Missing source controls, revoked credentials and incomplete pagination are explicit failure/insufficiency states. See zoho-integration.md and tally-integration.md for exact operator steps and official references.

## Full financial report sets for all listed systems

TallyPrime, Zoho Books, Busy Accounting, Marg ERP, SAP Business One, SAP S/4HANA, Oracle NetSuite, QuickBooks, Microsoft Dynamics and Xero accept source-labelled GL, trial-balance, journal and chart imports. Excel/CSV is also available as a generic source. Direct interfaces are described below; their credential configuration and live qualification are separate from report-upload support.

Use the “Import complete report set” button on a provider card. Upload three flat CSV or single-sheet XLSX files (combined maximum 64 MiB): a transaction-level GL, a functional-currency TB with source opening, period debit/credit and closing balances, and the chart of accounts. Map source headings or download the templates. Remove grouped headings/subtotal rows and include native transaction identifiers. Individual report imports retain the source-system identity too.

`GET /api/v1/connectors/{provider}/requirements` returns the report columns and live-testing prerequisites. `POST /api/v1/connectors/report-packages` accepts multipart `gl`, `tb`, `coa` and JSON `options` containing client/entity/period IDs, `source_system`, functional `currency`, optional `mappings` by report kind, `date_format`, `delimiter`, `encoding`, optional `supersedes_ids` by report kind, and optional independent `controls`. Each supplied control contains `reference`, `expected_rows`, `expected_debit`, and `expected_credit`; monetary totals use decimal strings. Source controls are operator-supplied evidence references, not independently authenticated attestations. Replacing an active population requires explicitly selecting its batch; a fresh report set never silently replaces it.

Preflight checks row normalization, unique posting/account IDs, account membership, balanced journals, consistent posting dates, account-level GL-to-TB movements, source opening/closing roll-forward and total opening/closing balance. Missing source balances fail rather than using calculated fallbacks. Failure creates no report batches. Success preserves all three original reports and returns `batch_ids` and a deterministic `package_id`; each batch's immutable snapshot options retain the package evidence before hashing. Retries of identical files/options reuse the existing import fingerprints. Explicit validation and activation are separate for each population. Ledger movements do not manufacture opening journals; use the TB population for source opening/closing reporting. Inventory, payroll, attachments and every ERP-specific subledger are not promised by this financial report contract.

## Required for live testing

For every product, provide its exact edition/version, a test company or sandbox, entity/base currency, financial-period start/end, and independently exported GL/TB/chart reports with source counts/totals. Include sales, purchases, receipts/payments, credit notes, tax, adjustments, opening balances, cancelled/optional entries where supported, and multi-currency examples when used. Provide authorized access through the application's secure setup or a secret manager; do not send passwords/tokens in chat.

- TallyPrime: a Windows machine with the test company open, localhost HTTP/XML enabled on port 9000, an HTTPS AuditOS URL, scope IDs, and an authorized import identity stored through the agent's OS credential vault. Run `uv run python ../agents/tally_agent.py CONFIG --set-refresh-token`, followed by the same command with `--kind all`.
- Zoho Books: data-center region, organization ID, an OAuth client configured with the exact frontend callback URL, read-only consent and `CONNECTOR_ENCRYPTION_KEY` plus `ZOHO_REDIRECT_URIS` configured on the server. Start authorization and organization selection from the Integration Center.
- Busy and Marg: edition/version and reviewed flat exports; native automation additionally needs vendor-approved API/SDK or partner access and its documentation.
- SAP Business One: company database, version and Service Layer read access.
- SAP S/4HANA: cloud/on-premise edition, company code, accounting ledger and approved read APIs/communication arrangement.
- NetSuite: account, subsidiary/accounting book and a read-only integration role with SuiteQL access.
- QuickBooks: Online needs a sandbox realm/OAuth app. Desktop requires a separately provisioned SDK-backed partner API and its documented contract; this change does not install a Desktop SDK agent.
- Dynamics: Business Central needs company GUID, directory tenant and Entra application/API permissions. Finance requires a separately provisioned partner API contract; it does not use the Business Central URLs.
- Xero: test organization, OAuth app and journal/report API entitlements.

No real vendor account was used for these changes. Production certification, automatic Tally service scheduling, resource-specific incremental synchronization, and qualification of proprietary partner contracts remain outstanding. This distinction must remain visible in release notes and UI.

## Direct API interfaces

The direct interfaces now execute HTTP API reads and stage imports without uploading reports. They reuse scoped encrypted credentials, Celery work authorization, private source storage, immutable snapshots and the existing import validation/reviewer activation flow. Connections can be created as drafts before credentials are available. A configuration save, OAuth exchange or successful extraction does not mean the account is production-qualified.

- QuickBooks **Online**: company-info identity check, paginated chart query including inactive accounts, accrual General Ledger report and native Trial Balance evidence. Report column metadata, company, period and report currency are checked. QuickBooks GL reports do not provide unique posting-line IDs; content/occurrence identifiers are scoped to each extracted snapshot. Full extraction replaces populations only through the existing explicit reviewer workflow. [Intuit API](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/generalledger).
- Xero: OAuth tenant authorization check, organisation base currency, chart, all accrual journal offsets through a terminal empty page, and native Trial Balance evidence. Short journal pages do not terminate extraction. GL uses native JournalLineID and NetAmount in base currency. The journal endpoint requires the vendor's approved tier/use case and security assessment; a denied entitlement fails explicitly. [Xero journals](https://developer.xero.com/documentation/api/accounting/journals/).
- NetSuite **SuiteQL/OneWorld**: verifies subsidiary and base currency, reads account masters and posting accounting lines from a deterministic SuiteQL query joined to transaction lines. Every line is restricted to the selected subsidiary and accounting book. OAuth refresh or an authorized access token is supported. REST query count/offset/hasMore are checked. The REST result limit causes an explicit failure, never a successful truncated import; narrow the period for large populations. Full historical TB/consolidation and non-OneWorld variants are not implied. [Oracle SuiteQL](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_157909186990.html).
- SAP **Business One Service Layer**: confidential Login session, chart and date-filtered journal headers with a separate full-detail read for each journal. The company LocalCurrency is checked through CompanyService_GetAdminInfo. Local-currency Debit/Credit and native account/journal/line identities are normalized; source XML/JSON retains other fields. The service root must match the installed version and be allowlisted. Localized currency aliases must be qualified explicitly rather than silently treated as ISO codes. [SAP API reference](https://help.sap.com/doc/056f69366b5345a386bb8149f1700c19/10.0/en-US/Service%20Layer%20API%20Reference.html).
- SAP **S/4HANA**: OData ledger-view mode reads the deployed G/L line-item entity and filters company, ledger and posting dates. Supply the exact service root/entity from deployed metadata, and an account-master path if chart extraction is required. Entry-view mode reads operational journal items and is explicitly labelled limited coverage: SAP documents that ledger-only postings can be absent. Basic communication-user or securely supplied bearer-token authorization is supported. Company-code currency is verified per line. [Ledger API](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/3ab6e6fc510f4840a5508e126ef01e22/80214b5ede2f4e97b640137a4eca208a.html), [SAP entry-view limitation](https://userapps.support.sap.com/sap/support/knowledge/en/2821106).
- Dynamics **Business Central v2**: verifies the selected company GUID, then reads accounts and period-filtered generalLedgerEntries using pinned OData next links. Supports Entra application credentials or an authorized access token. Company Information currencyCode is checked against the AuditOS entity; standard G/L amounts are local-currency amounts. The standard API lacks Transaction No.; document-number/date grouping is disclosed in the manifest, rather than asserted as native journal identity. [Microsoft resource](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_generalledgerentry).
- **BUSY/Marg**, plus **QuickBooks Desktop/Dynamics Finance** variants: a configurable direct partner-API transport is implemented, including company/currency verification, encrypted bearer/API-key/basic credentials where supported, documented endpoint paths, response-field mappings, strict continuation evidence, and GL/COA/optional TB normalization. No CSV/XLSX intermediary is used. This is not an invented universal BUSY/Marg API or a bundled vendor SDK. Vendor-specific production readiness still requires the actual contract to be configured and qualified. BUSY explicitly directs API integrations to channel partners; Marg provisions gateway URLs and packages. [BUSY official requirements](https://busy.in/faqs/third-party-services/integration/10/), [Marg API Gateway](https://margcompusoft.com/Package/Packages.aspx).

Native Trial Balance responses from QuickBooks/Xero are retained as original evidence. Their presentation/YTD columns are not relabelled as period movements or fabricated into canonical TB rows. Native TB rows supplied by a partner endpoint require explicit opening/closing values, balanced totals and GL movement agreement before staging. No connector claims source completeness merely because debits equal credits.

### Setup and API lifecycle

1. Set `CONNECTOR_ENCRYPTION_KEY`. In container deployments the new origin/redirect settings are forwarded to both backend and workers.
2. For SAP and partner services, set `CONNECTOR_ALLOWED_ORIGINS` to the exact trusted HTTPS origin(s), including nonstandard ports, for example `["https://erp.example:50000"]`. API roots and all next links are pinned to the configured origin and service path. TLS verification remains enabled; redirects, link-local addresses and escaped pagination links fail. Configure a trusted certificate for on-premise systems rather than disabling TLS.
3. For browser OAuth, register the exact frontend callback (currently `/integrations/zoho/callback?native=1`, shared with the accounting callback component) with Intuit/Xero and in `CONNECTOR_REDIRECT_URIS`. State is random, hashed, scoped to the row-locked connection, expires in ten minutes and is consumed once. QuickBooks callback realm ID must match the selected company. NetSuite uses an authorized refresh/access token; Business Central supports Entra client credentials.
4. Create a scoped `/api/v1/accounting/connections` resource with provider/name and optional `config`/`credentials`, or create a draft in the Integration Center and fill its direct-API panel later. `GET /api/v1/connectors/{provider}/requirements` publishes editions, configuration fields, credential field names and documentation links. Credentials are never returned.
5. `PATCH /api/v1/connectors/native/{id}/configuration` saves the typed non-secret `config` and merges supplied `credentials`. Omitted fields retain stored secrets; the UI does not submit blank credential fields. `replace_credentials=true` explicitly resets credentials. Configuration changes invalidate an in-progress OAuth state. The UI clears entered secrets after saving.
6. `POST /api/v1/connectors/native/{id}/authorize` takes an allowlisted `redirect_uri`; `/callback` takes `code`, `state` and QuickBooks `realm_id`. Alternatively configure supported secure credentials directly. No browser authorisation is offered for a partner-API edition.
7. Optional `control_reference`, `expected_gl_rows`, `expected_gl_debit` and `expected_gl_credit` configuration fields accept independently supplied source controls without requiring a file upload. A reference is required for supplied controls; mismatches fail before staging. Controls are retained in GL import options and sync lineage. A match does not automatically assert completeness.
8. `POST /api/v1/connectors/native/{id}/sync` dispatches an authorized background job; `background=false` is intended for small diagnostic extracts. `GET /api/v1/connectors/native/sync-runs/{id}` exposes the scoped status, private-object references, scope verification, validation errors and `derived_import_batch_ids`. Token refreshes are re-encrypted even after a known extraction failure. Jobs report failed source runs as failed.
9. Source pages are preserved before normalization. No derived batches are staged until extraction and financial preflight succeed. Duplicate source identities, inconsistent companies/currencies/periods, missing accounts and unbalanced journal groups fail. Successful batches still require normal validation and explicit reviewer activation. GL/COA coverage is source-specific and disclosed; missing opening balances are never fabricated.

Partner API editions require a JSON company response whose configured identity/currency fields match the selected company, followed by paginated JSON accounts/GL/optional-TB responses. Configure `rows_key` (default `items`) and `next_key` (default `next`). The next field must be present and either contain an approved continuation URL or null/empty for exhaustion. `mappings` by `coa`, `gl`, `tb` map canonical fields to dotted source JSON field paths. GL source IDs must be native and stable. Endpoint/field names must come from the licensed vendor/partner contract. The transport deliberately does not guess them or call business-write endpoints.

### Deferred live qualification

Normal tests use `httpx.MockTransport` and synthetic fixtures; they do not contact vendor accounts. The optional read-only check is `uv run pytest tests/phase2/test_live_native.py -q`. Enable `LIVE_NATIVE_CONNECTOR=1` only after configuring `NATIVE_PROVIDER`, non-secret `NATIVE_CONFIG_JSON`, secure `NATIVE_CREDENTIALS_JSON`, `ACCOUNTING_PERIOD_START`, `ACCOUNTING_PERIOD_END`, `ACCOUNTING_FUNCTIONAL_CURRENCY`, and independent `NATIVE_EXPECTED_GL_ROWS`, `NATIVE_EXPECTED_GL_DEBIT`, `NATIVE_EXPECTED_GL_CREDIT`. Custom services additionally need `CONNECTOR_ALLOWED_ORIGINS`. Run once for each provider/edition. It compares actual extracted rows and base amounts to source controls without writing business data to the vendor. Credentials, tenant entitlements, deployed metadata and partner contracts can be supplied later; none were used during development.
